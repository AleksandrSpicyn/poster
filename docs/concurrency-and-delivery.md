# Конкурентное выполнение и доставка событий

## Область применения

Документ разделяет конкурентное выполнение внутри операции, фоновые jobs и
доставку событий клиентам. Это разные механизмы с разными гарантиями. Конкретный
runtime, queue driver, broadcaster и доступные API проверяются по установленным
версиям и конфигурации; собственный runner приложения не является API Laravel.

В стандартном профиле orchestration находится в подходящем service/use case,
jobs/listeners — в общих каталогах. В модульном профиле они принадлежат модулю.
Правила зависимостей задаёт [architecture.md](architecture.md).

## Когда полезна конкурентность

Используйте её для действительно независимых операций при измеримой пользе.
Сначала сравните реалистичный последовательный путь: batch query или устранение
N+1 может быть проще и быстрее запуска нескольких workers.

До распараллеливания проверьте:

- отсутствие зависимости по данным и порядку побочных эффектов
- actor/tenant scope и lifecycle передаваемого контекста
- serialization и доступность DI/config в worker
- transaction/connection boundaries и видимость ещё не committed writes
- ограничения connection pool, CPU, памяти, provider limits и timeout chain
- сбор ошибок, частичный результат, отмену и поведение fallback

Параллельные workers не разделяют автоматически транзакцию родительского запроса.
Нельзя выдавать частичный write за атомарную операцию. Последовательный fallback
не должен повторять уже подтверждённые внешние эффекты. Таймаут ожидания сам по
себе не доказывает, что удалённая операция остановилась.

## Фоновые операции и retries

Передавайте необходимый минимальный контекст и стабильные идентификаторы.
Задайте политику повторной загрузки состояния и проверки прав; не захватывайте
HTTP request или mutable singleton в queued payload.

Определите timeout, число попыток, backoff, retryable ошибки, idempotency key и
поведение после окончательного отказа. Не выполняйте необратимый external effect
повторно только потому, что подтверждение первой попытки потерялось.

Если job или событие зависит от committed данных, используйте предусмотренное
после-commit поведение. Сам commit и отправка во внешнюю систему обычно не
атомарны; при требовании надёжной доставки рассмотрите transactional outbox
или существующий durable механизм вместо обещания exactly-once.

## Доставка клиентам

Укажите гарантию каждого канала: возможны потеря, повтор, задержка и изменение
порядка. WebSocket-уведомление само по себе не гарантирует восстановление после
reconnect. Определите authoritative state и способ resync/replay/cursor по
контракту системы, а не рассчитывайте только на live-соединение.

Payload содержит разрешённые данные, достаточную identity/version и понятную
семантику изменения. Клиент идемпотентно обрабатывает повторы и не перезаписывает
новое состояние устаревшим событием. Проверяйте channel authorization и scope.
Не обещайте глобальный порядок, если транспорт гарантирует лишь локальный.

## Проверка

Покройте успешную обработку, timeout/ошибку, частичный результат, retry,
rollback-before-dispatch, duplicate/out-of-order и reconnect по применимости.
Fakes проверяют orchestration; worker lifecycle, реальную сериализацию и transport
гарантии нужно подтверждать отдельным integration/runtime запуском.

Benchmark сравнивает одинаковый объём данных, семантику и условия. Укажите среду,
измеряемую границу и ограничения; локальное ускорение не является SLA endpoint.
Связанные правила: [testing.md](testing.md), [authorization.md](authorization.md),
[activity-log.md](activity-log.md).

## Пример transaction и dispatch после commit

Фрагмент Action предполагает существующие `$article`, `$actor` и queued job
`IndexArticle`; он показывает порядок, а не определяет способ индексации:

```php-fragment
DB::transaction(function () use ($article, $actor): void {
    $article->is_published = true;
    $article->save();

    IndexArticle::dispatch($article->getKey(), $actor->getKey())->afterCommit();
});
```

Без настроенного после-commit поведения worker может увидеть старое состояние.
Даже `afterCommit()` не превращает commit БД и отправку брокеру в одну атомарную
операцию; при требовании durable доставки нужен дополнительный механизм.

## Пример идемпотентного consumer

Для канала, присылающего полное состояние сущности с монотонной `version`:

```javascript
function applyArticleEvent(current, incoming) {
  if (incoming.id !== current.id || incoming.version <= current.version) {
    return current;
  }

  return { ...current, ...incoming };
}
```

Этот алгоритм подходит snapshots. Для delta-events пропущенная версия может
требовать resync, а не применения следующего delta поверх неполного состояния.
Server также должен авторизовать подписку и исключить лишние поля payload.

## Что сравнить перед конкурентной оптимизацией

| Проверка | Последовательный путь | Конкурентный путь |
|---|---|---|
| Результат | Поля, scope, ordering | Тот же контракт |
| Ошибка одного источника | Полный отказ или partial contract | Та же согласованная семантика |
| Query/external calls | Реальное число и размеры | Без случайного дублирования |
| Время | Повторяемый baseline | Измеренное распределение, не один удачный запуск |
| Ограничения | Connections, память | Дополнительный worker/pool budget |

Не запускайте independent-looking writes параллельно, пока не проверены общие
locks, unique constraints, порядок событий и способность safely retry.
