## 1. Цель, границы и критерий результата

Poster должен создавать связанные эпизоды произвольной темы: реалистичную драму,
детский мультфильм и другие форматы. Общий конвейер использует настройки аудитории,
стиля, языка, звука и повествования. Отдельные движки для каждого жанра не нужны.

Обязательные возможности:

- Ручной, сгенерированный и отредактированный сценарий с версиями.
- Постоянные персонажи и загрузка созданных в другом приложении референсов.
- Использование конкретной версии внешности и голоса в конкретном эпизоде.
- Генерация по отдельным планам, хранение и выбор дублей.
- Продолжение незавершённой сцены от выбранного финального состояния и кадров.
- Новый план или новая сцена с сохранением событий и состояния персонажей.
- Проверка и утверждение сценария, монтажа и фактически произошедших событий.
- Публикация утверждённого эпизода отдельным действием.
- Сохранение самостоятельных shorts, их истории и публикаций.

Первый сквозной критерий приёмки: один сериал, два персонажа, три коротких эпизода,
продолжение открытой сцены, переход к новой сцене и замена одного дубля.
Проверяются как состояние приложения, так и качество реально полученного видео.
Качество внешности и стыка кадров нельзя подтвердить одними fakes.

Начальная модель истории линейная. Сезоны, альтернативные сюжетные ветки,
совместное редактирование в реальном времени и автоматический выпуск без просмотра
не входят в первую версию. Их отсутствие не ограничивает тему или визуальный стиль.

## 3. Архитектурные принципы и их применение

Основная форма — существующее Laravel-приложение с фоновыми workers.
БД хранит авторитетное состояние; очередь доставляет работу; файловое хранилище
хранит медиа. Redis используется для координации и ограничений конкурентности.
Выделение микросервисов для первой версии не требуется.

Ниже зафиксировано применение ООП, SOLID, DRY и KISS к конкретным границам проекта.

| Принцип | Конкретное решение | Что проверить на review |
|---|---|---|
| SRP | Controller отвечает за HTTP, Action — за один сценарий, Task — за отдельную операцию | Генерация сценария не публикует видео и не обновляет историю сериала |
| OCP | Протокол внешнего генератора находится в существующем адаптере | Новый провайдер не добавляет проверки имени в монтаж и память |
| LSP | Общий контракт имеет одинаковые результаты и категории ошибок; допустимые режимы заданы capabilities | Сценарий не предполагает, что любой драйвер умеет extension или reference audio |
| ISP | Текст, изображения, видео и публикация сохраняют отдельные контракты | Нет общего интерфейса со множеством неприменимых методов |
| DIP | Внешние эффекты доступны через контракты; обычные Tasks остаются конкретными классами | Нет интерфейса и фабрики для каждого внутреннего Task |
| DRY | Одна схема сценария, общие нормализованные ошибки и правила перехода | PHP и Vue не поддерживают независимые наборы статусов |
| KISS | Линейная история, обычные таблицы, JSON-снимки контекста, явные переходы | Нет универсального workflow engine, event sourcing или DSL без текущей задачи |
| ООП | Типизированные входы/результаты, инкапсуляция переходов, композиция | Статус нельзя произвольно изменить из контроллера или Resource |
| YAGNI | Новая абстракция вводится на подтверждённой границе | Пример структуры не превращён в массовое scaffolding |

Применяется `Controller → Action.run() → Task.run() → Eloquent/интеграция`.
Job или CLI вызывает соответствующий Action. Новые Actions не вызывают обычные
Actions, Tasks не образуют цепочки Task → Task. Общая операция переиспользуется
через Task с реальной ответственностью. Repository-слой не добавляется.
Общая транзакция нескольких операций координируется Action; отдельные записи
выполняют Tasks в той же connection/transaction.

Модели содержат связи, casts и локальные инварианты; сетевые вызовы, очередь,
FFmpeg и сценарное orchestration в моделях не размещаются.

## 4. Модель данных и источники истины

### 4.1. Основные сущности

Это целевая схема для полного первого сценария. Таблицы вводятся по этапам,
а их окончательные типы/FK проверяются через Boost database-schema и миграции.

| Таблица / модель | Основные поля и связи | Инвариант |
|---|---|---|
| `series` / `Series` | `project_id`, name, паспорт мира/формата, `specification_version`, `continuity_version`, `canonical_assembly_id`, архивирование | Серии одного сериала используют совместимый контекст |
| `characters` / `Character` | `series_id`, постоянный ID, имя, `current_revision_id`, архивирование | Идентичность сохраняется при смене одежды и референсов |
| `character_revisions` / `CharacterRevision` | `character_id`, `number`, spec JSON, voice spec, автор/дата утверждения | Утверждённая версия и её файлы неизменяемы |
| `episodes` / `Episode` | `series_id`, `number`, `predecessor_episode_id`, `current_revision_id`, `accepted_assembly_id`, `lock_version`, validity | Номер уникален в сериале; предшественник из того же сериала |
| `episode_revisions` / `EpisodeRevision` | `episode_id`, `number`, script schema version, цель, контекст JSON/hash, pinned character revisions, `source_assembly_id`, status | После утверждения текст и входной контекст не редактируются |
| `episode_revision_characters` | `episode_revision_id`, `character_revision_id` | FK защищают закреплённые версии; состав одной версии сценария фиксируется при утверждении |
| `scenes` / `Scene` | `episode_revision_id`, position, место/время, цель, ожидаемые состояния, planned closure | Сцена относится к одной версии сценария |
| `shots` / `Shot` | `scene_id`, position, `duration_ms`, действие, камера, реплики, transition mode, source anchor | План — одна единица генерации; длительность и зависимости явные |
| `prompts` / `Prompt` | Существующие поля + nullable `shot_id`, номер дубля, snapshot/hash входа | Одна запись — один дубль; старые записи имеют `shot_id = null` |
| `generation_operations` / `GenerationOperation` | `prompt_id`, stage, provider/model, request/hash, idempotency key, status, external ID, error category, timestamps | Один внешний запуск стадии имеет собственную долговечную запись |
| `episode_assemblies` / `EpisodeAssembly` | `episode_revision_id`, номер сборки, manifest/hash, status, media, confirmed continuity JSON, автор/дата принятия | Утверждается конкретный монтаж с конкретными дублями |
| `publication_requests` / `PublicationRequest` | `episode_assembly_id`, `channel_id`, payload snapshot, status, remote/container ID | Запрос публикации сохраняется до внешнего эффекта |
| `posts` / `Post` | Старый `prompt_id` + nullable `episode_assembly_id` и ссылка на receipt | История подтверждённой публикации указывает на точную версию видео |

Файлы остаются в Media Library; отдельная универсальная таблица Assets не вводится.
Референсы прикрепляются к `CharacterRevision`, итоговое медиа — к `Prompt` или
`EpisodeAssembly`. Метаданные ракурса, checksum и назначения — у соответствующего
media. Используемые media нельзя физически удалять заменой текущей карточки.

Локации, реквизит и отношения сначала хранятся как валидируемые структуры
с устойчивыми ID внутри паспорта/состояния. Отдельные каталоги для них нужны
при появлении самостоятельного редактирования, поиска и повторного использования.

### 4.2. Ограничения и индексы

- FK и уникальные `(series_id, number)`, `(character_id, number)`,
  `(episode_id, number)`, `(episode_revision_id, position)`, `(scene_id, position)`.
- Номер дубля уникален внутри shot. У операции уникальна комбинация
  `(prompt_id, stage, submission_number)`: повтор polling не создаёт новую
  операцию; явно запрошенный новый дубль — новый Prompt.
- Если подтверждён безопасный fallback, отдельная попытка отправки имеет свой
  `submission_number` и receipt. Под одним lock проверяется окончательный
  однозначный отказ предыдущей отправки; она сохраняется, а не перезаписывается.
- Уникальные operation idempotency key и `(channel_id, episode_assembly_id)`
  у запроса публикации предотвращают повтор одного логического запуска.
- Индексы для выборок дочерних сущностей и `(status, next_check_at)` у фоновых
  операций. Потребность дополнительных индексов подтверждается запросами.
- Обычный FK не проверяет принадлежность предшественника, персонажа, дубля
  или канала нужному сериалу/проекту: scoped validation и Action проверяют её.
- У связей закреплённых персонажей уникальная пара FK; snapshot формируется
  из этих связей при утверждении, а не редактируется как отдельный список ID.
- `selected_prompt_id` не хранится параллельно с manifest как второй источник
  истины. Выбранные дубли определяет manifest конкретной сборки.
- Не поддерживать одновременно JSON сценария и отдельные scenes/shots как
  независимо редактируемые копии. Нормализованные scenes/shots — рабочая модель;
  JSON экспорт/снимок генерируется из неё при фиксации версии.

### 4.3. Версии и совместимость

Паспорт сериала имеет версию; его содержимое фиксируется в контексте сценария.
CharacterRevision и EpisodeRevision отделяют постоянную идентичность от версии.
Draft допускает редактирование с `lock_version`; approved замораживается.
Следующее изменение создаёт новый draft с происхождением от предыдущей версии.
Существующие дубли и принятые сборки остаются привязаны к старой версии.

Снимки JSON имеют `schema_version`; читать старые версии следует явно.
Hash строится из детерминированной сериализации валидированных данных и checksum
медиа. В hash не включаются временные URL и время выполнения. Hash служит
идентичностью входа, но не обещает идентичный результат генеративной модели.

`Prompt.generated` сохраняет старое значение «файл собран». Оно не означает
утверждение дубля, обновление канона или публикацию.
Для сериалов `GenerationOperation` — источник статуса внешней операции;
старые ID/URL на Prompt при необходимости обновляются одним Task как проекция
для существующего UI. Не допускаются два независимо работающих poller одной задачи.

Удаление пустых сущностей возможно по явным правилам; использованные сериалы,
персонажи и версии архивируются. Учесть новые связи в существующем DeleteProject:
проект с сериалом нельзя считать пустым только по prompts/channels.

## 5. Состояния и разрешённые переходы

Не объединять сценарий, платную операцию, монтаж и публикацию в один общий status.
Наборы значений оформляются отдельными enum с `App\Traits\EnumTrait`.
В DTO используются enum-типы, на SQL/HTTP-границах — backed values.

| Объект | Основные состояния | Правила перехода |
|---|---|---|
| Версия сценария | `draft → approved`, старая версия может быть `superseded` | Утверждение проверяет структуру, ссылки и актуальность исходного контекста |
| Внешняя операция | `planned → submitting → submitted → running → succeeded` | Сохранять receipt до запроса, remote ID после подтверждения; polling может сразу получить success |
| Отказ операции | `failed`, `submission_unknown`, `cancelled` | Unknown запрещает автоматическую новую отправку; cancelled требует подтверждённой семантики |
| Сборка | `draft → queued → building → ready → accepted`; возможен `failed` | Перед build manifest замораживается; принятый файл не перезаписывается |
| Актуальность эпизода | `current`, `requires_review` | Это отдельный признак зависимости, а не переписывание исторического accepted |
| Публикация | `planned → submitting → processing → published`; `failed` / `submission_unknown` | Instagram container сохраняется до второго шага; Post создаётся после подтверждения |

Для каждого перехода определить допустимое исходное состояние, expected version,
предусловия, сохраняемые поля, внешние эффекты и обработку повтора.
Повтор уже выполненного перехода возвращает существующий результат.
Конфликт входной версии возвращается явно, не маскируется успехом.

Состояние `submitting`, оставшееся после падения worker, не означает, что запрос
не был отправлен. После истечения срока проверки оно требует reconciliation
или перевода в `submission_unknown`, а не повторной оплачиваемой отправки.

Отмена запланированного шага прекращает дальнейшую работу. Для уже запущенной
внешней задачи «остановить конвейер» и «провайдер подтвердил отмену» различаются.
Поздний результат сохраняется как receipt, но не выбирается и не публикуется.

## 6. Контракты генераторов и прикладные границы

### 6.1. Текст и изображения

- Добавить структурированный вывод сценария в существующую границу Laravel AI /
  Codex. Использовать возможности установленной версии SDK и CLI; не создавать
  параллельный обходной клиент с отдельной авторизацией.
- Данные проходят JSON schema, DTO validation и предметные проверки. Валидный
  JSON сам по себе не подтверждает допустимость персонажей, таймингов и переходов.
- Ответ модели не записывается напрямую в Eloquent через произвольный payload.
- Ошибка структуры допускает ограниченное исправление, затем понятный отказ;
  до успешной проверки запуск изображения/видео запрещён.
- Поздний ответ генерации создаёт отдельный draft/результат для своего snapshot.
  Он не перезаписывает сценарий, который пользователь успел изменить.
- Расширить ImageGenerator request данными референсов. CodexProcess получает
  только необходимые проверенные копии файлов во временном каталоге.
- Сохранить изоляцию CLI, запрет shell tools и отсутствие автоматического
  перехода с подписки на платный API при ошибке.

### 6.2. Видео

Заменить примитивную пару `imageUrl, prompt` типизированным request DTO.
Предлагаемые поля: prompt, mode, media references, duration, aspect ratio,
resolution, audio mode, model и применимые provider options.
Значения по умолчанию разрешаются до отправки и входят в сохранённый snapshot.

| Режим запроса | Обязательный вход | Предварительная проверка |
|---|---|---|
| `first_frame` | Подготовленный первый кадр, при поддержке — последний кадр | Форматы, размеры, длительность, совместимость параметров |
| `references` | Выбранные референсы персонажей/окружения | Число, роли, допустимые сочетания и доступность модели |
| `extend` | Принятый исходный видеофрагмент и инструкция продолжения | Поддержка extension, ограничения входного видео и выходного формата |

Режим перехода сюжета и режим API — разные enum. `continue_scene` может быть
реализован через extension или через final-frame → first-frame. Выбор следует
из проверенных возможностей модели, а не из названия сюжетного режима.

Драйвер возвращает типизированные capabilities по конкретной модели, нормализованные
receipt/result и категории ошибок. Общему orchestration не нужны provider-specific
payload. Незнакомые параметры и неподдерживаемые комбинации отклоняются до оплаты.

Не обещать точный первый кадр одновременно с произвольными omni-референсами,
если API не поддерживает такое сочетание. Вариант подготовки: создать первый
кадр по внешности и состоянию, затем отправить его в frame-based режим.
Другой вариант — проверенный reference/extend режим с собственной оценкой стыка.
Документация Seedance описывает эти ограничения:
[создание задачи](https://docs.byteplus.com/en/docs/ModelArk/create-video-generation-task-api),
[режимы продолжения](https://docs.byteplus.com/en/docs/ModelArk/seedance-2-5-prompt-guide?redirect=1).

Результат операции содержит remote ID, фактические provider/model, источники
видео/аудио/последнего кадра, доступные usage и метаданные. Временные ссылки
скачиваются в собственное хранилище до их истечения. Фактический источник звука
по-прежнему определяется выбранным драйвером.

Существующие Seedance/Hailuo/Runway переводятся на общий request в одном
совместимом изменении с тестами старого first-frame пути. Резерв разрешается
только для совместимого режима и однозначно не созданной задачи.

### 6.3. Размещение и владельцы сценариев

| Область | Примеры Actions | Примеры Tasks / внешних границ |
|---|---|---|
| Сериалы | `SaveSeriesAction` | Сохранение паспорта, выборки с scope |
| Персонажи | `SaveCharacterRevisionAction`, `ApproveCharacterRevisionAction` | Проверка файлов, сохранение версии и Media Library |
| Сценарий | `GenerateEpisodeScriptAction`, `ApproveEpisodeRevisionAction` | Сбор контекста, генерация/валидация, сохранение scenes/shots |
| Дубли | `RequestShotGenerationAction`, `SubmitShotGenerationAction`, `CompleteShotGenerationAction` | Claim операции, адаптер, persistence receipt/result |
| Монтаж | `RequestEpisodeAssemblyAction`, `BuildEpisodeAssemblyAction` | Валидация manifest, FFmpeg, регистрация медиа |
| Канон | `AcceptEpisodeAction` | Проверка зависимостей и атомарное продвижение истории |
| Публикация | `RequestEpisodePublicationAction`, `CompleteEpisodePublicationAction` | Receipt, существующие publishers, запись Post |

Примеры имён описывают ответственность. Создавать только используемые сценарии,
не весь список заранее. Каталоги остаются стандартными: `app/Actions`, `app/Tasks`,
`app/Data`, `app/Enums`, `app/Models`, `app/Jobs`, `app/Http`, `tests`.
Подкаталоги уточняют область; `app/Modules` и новые базовые слои не вводятся.

## 7. Память, канон и алгоритм продолжения

### 7.1. Содержимое контекста

Снимок содержит schema version, версию паспорта, pinned character revisions,
ID/checksum исходной принятой сборки и версию continuity. Сюжетная часть включает
подтверждённые события, знания и отношения персонажей, открытые конфликты,
текущее место/время и состояние незавершённой сцены.

Факт хранит источник: сборку, shot и при необходимости таймкод. Сводка может
пересоздаваться, но не заменяет исходные подтверждённые факты.
Ожидаемый финал сценария и подтверждённое окончание монтажа — разные данные.
Результат автоматического анализа сначала сохраняется как предложение.

Сбор контекста детерминирован: обязательные правила → активные персонажи →
текущее состояние → нужные открытые линии → ограниченные исторические сводки.
Ввести лимит размера/токенов и тестировать переполнение. Сначала сокращать
второстепенную историю; обязательный текущий контекст нельзя молча обрезать.
Если он не помещается, остановиться с объяснимой ошибкой.
Vector DB и RAG добавляются только при подтверждённой проблеме поиска по истории.

### 7.2. Подготовка следующего фрагмента

1. Загрузить сериал и конкретную принятую исходную сборку в его scope.
2. Проверить актуальность canonical predecessor и права операции.
3. Прочитать подтверждённое состояние последней сцены и сценарный переход.
4. Для `continue_scene` зафиксировать open scene, source media/checksum,
   финальный таймкод, позы, предметы, одежду, движение и свет.
5. Для `new_shot` сохранить место/время и состояние, разрешив новую камеру.
6. Для `new_scene` сохранить историю/персонажей, явно описав смену места/времени.
7. Подобрать только необходимые ракурсы референсов. Порядок и сопоставление
   «персонаж → изображения» фиксируются в запросе; identity не выводится из имени файла.
8. Сохранить snapshot и dependencies; затем генерировать или редактировать сценарий.
9. Перед отправкой и принятием повторно проверить версию зависимостей.

Утверждённые мастер-референсы остаются источником внешности при каждом плане.
Сгенерированный вчера кадр не становится новой версией персонажа автоматически:
иначе ошибки внешности будут накапливаться по цепочке. Для режима, не принимающего
их одновременно с continuation input, применять проверенную подготовку кадра
и визуальную проверку результата относительно закреплённой CharacterRevision.

У незавершённой сцены по умолчанию предлагается продолжение, у законченной —
новая сцена. Пользователь может изменить предложение через сценарий.
`continue_scene` не должен молча применяться к закрытой сцене: требуется явное
изменение исходного решения/версии. Последовательные планы внутри эпизода
также могут зависеть от выбранного дубля предыдущего плана.

Источник точки продолжения — фактический финал после trim/montage. Последний
кадр провайдера может не совпадать с концом принятого монтажа.
Сохранять кадр и короткий хвост, извлечённые FFmpeg из выбранного участка,
а также выбранный пользователем таймкод. Источник должен быть декодируемым.

### 7.3. Принятие эпизода и конкурентные изменения

`AcceptEpisodeAction` проверяет готовый файл, frozen manifest, принятые результаты
всех планов, подтверждённую continuity и актуальный predecessor.
В короткой транзакции блокирует сериал/эпизод, сравнивает expected versions,
фиксирует accepted assembly и сдвигает canonical head с увеличением
`continuity_version`. Сетевые вызовы и FFmpeg в этой транзакции запрещены.

В первой версии следующий канонический эпизод принимается только после
предшественника. Два worker не могут одновременно продвинуть одну и ту же голову
в разные продолжения. Черновые будущие сценарии допустимы, но не считаются каноном.
Внутри эпизода зависимые планы ждут выбора исходного дубля; независимые могут
генерироваться параллельно в пределах квот.

Замена более ранней принятой сборки:

- Сохраняет старую сборку, её файлы, факты и публикации как историю.
- Переставляет canonical head на новую принятую сборку заменённого эпизода.
- Помечает зависимые эпизоды и сборки `requires_review`; публикация их новых
  версий блокируется до проверки и принятия последовательности.
- Не запускает каскадную платную перегенерацию и не удаляет уже опубликованное.
- Показывает пользователю список затронутых продолжений.

Смена выбранного дубля внутри draft-сборки аналогично инвалидирует производные
материалы, чьи snapshots ссылаются на старый source. Переиспользование неизменённых
результатов возможно после явной проверки зависимостей.

## 8. Надёжность, очереди и платные эффекты

### 8.1. Долговечная операция вместо состояния только в job

1. В транзакции создать Prompt, frozen input snapshot и операцию `planned`.
2. После commit поставить job с ID операции и ожидаемой версией.
3. Worker атомарно переводит `planned → submitting`; конкурентный worker не отправляет запрос.
4. Вне транзакции выполнить внешний вызов с idempotency key, если API его поддерживает.
5. Сохранить external ID/result или категорию ошибки; polling использует тот же ID.
6. После локального сохранения результата создать следующий необходимый шаг
   идемпотентно и отправить его после commit.

`afterCommit()` не делает commit БД и доставку в очередь одной атомарной операцией.
Поэтому добавить ограниченный reconciler: находить `planned` без прогресса,
восстанавливать доставку, продолжать polling известных remote ID и выполнять
недоставленные внутренние переходы. Не отправлять заново `submitting/unknown`.
Существующих таблиц операций/публикаций достаточно как durable intent;
общий event bus/outbox framework в первой версии не требуется.

Job uniqueness и Redis locks уменьшают дубли, но инварианты защищаются также
уникальными ключами и сравнением состояния в БД. Перед выполнением worker заново
проверяет отмену, зависимости и допустимость шага.

### 8.2. Политика ошибок

| Ситуация | Действие |
|---|---|
| Неверные входные параметры / отсутствует capability | Отказ до внешнего запроса |
| Однозначный отказ без создания задачи | Ограниченный retry/fallback по политике адаптера |
| Timeout запуска / потерянный ответ / неоднозначный 5xx | `submission_unknown`, reconciliation, без слепого fallback |
| Временная ошибка polling известного ID | Backoff и повтор чтения, без новой задачи |
| Терминальный отказ генерации | Сохранить причину; новый дубль только отдельным действием |
| Ошибка скачивания готового файла | Повтор скачивания того же результата в пределах срока URL |
| Ошибка FFmpeg | Повтор локальной сборки по тому же frozen manifest |
| Устаревший snapshot | Сохранить результат для просмотра, запретить автоматический выбор/принятие |
| Неизвестный результат публикации | Проверка remote receipt, без автоматической повторной публикации |

Считать exactly-once для внешних систем недостижимой гарантией без поддержки
со стороны API. Цель — повторяемые внутренние переходы и предотвращение
известных повторных внешних эффектов с явным учётом неизвестного исхода.

### 8.3. Ресурсы и стоимость

Разделить очереди долгого FFmpeg, отправки/опроса провайдеров и лёгких переходов.
Настройки workers выбирать по измеренным CPU/RAM, квотам и фактической длительности.
HTTP timeout меньше timeout job, а timeout worker/job меньше `retry_after`
с запасом. Lease lock должен покрывать критическую секцию; истечение lease
не служит разрешением повторно оплатить неизвестную операцию.

Сохранить общий lock Codex на используемый CODEX_HOME; конкурирующую работу
откладывать, а не удалять защиту авторизации. Общие квоты считать по аккаунту
провайдера, а не отдельно по каждому сериалу. Ключи координации не содержат секрет.

Ограничить длительность, размер входов, число дублей и одновременных запусков.
До отправки сохранять оценку и резерв лимита в короткой транзакции; неизвестный
платный исход сохраняет резерв до reconciliation. Если точного тарифа/usage нет,
явно показывать оценку/неизвестное значение. Ручной retry не обходит лимит.
Оценка нагрузки: эпизоды × планы × среднее число дублей; отдельно считать
создание кадров, озвучку, сборку и хранение.

## 9. Медиа, монтаж и звук

- Оригиналы референсов, черновики и контекст хранятся приватно. Авторизованный
  UI получает временный/проксируемый доступ. Публичный экспорт создаётся по
  явной политике; путь хранения не является проверкой доступа.
- Первая версия принимает загрузку файлов. Импорт произвольного URL не нужен;
  если он добавляется, требуются ограничения схемы, DNS/IP и redirect для SSRF.
- До конвертации проверять размер, фактический MIME, dimensions, число кадров
  анимации и ресурсные пределы. Исключить произвольные пути/аргументы FFmpeg.
- Подготовка референса сохраняет оригинал. Производные файлы имеют checksum,
  связь с версией и назначение; не добавлять conversions без потребителя.
- Передача провайдеру использует поддержанный transport: ограниченный Base64,
  временный URL с достаточным TTL или зарегистрированный asset. В БД хранится
  стабильный media ID, а временный URL формируется при отправке.
- Manifest сборки содержит ordered shot/Prompt/media IDs, checksums, trim in/out,
  параметры переходов, audio tracks, captions и нормализацию формата.
- До сборки проверять наличие файлов, codecs, FPS, размеры, диапазоны trim
  и итоговую длительность. Использовать явную политику нормализации.
- Сначала собирать во временный файл, проверить декодирование и потоки,
  затем зарегистрировать в Media Library. Ошибка не даёт состояние `ready`.
- Для extension проверить, возвращает ли API только продолжение или исходник
  вместе с ним. Зафиксировать контракт адаптера, чтобы монтаж не дублировал хвост.
- Для каждого фрагмента определить источник речи, музыки и эффектов. Не смешивать
  непреднамеренно нативный soundtrack и второй полный soundtrack.
- Голос персонажа фиксируется в версии. Выбор нативной речи либо TTS/lip-sync
  зависит от прототипа; новые платные интеграции/зависимости согласуются отдельно.
- Уборка удаляет только собственные временные/неиспользуемые файлы после периода
  удержания. Принятые медиа и референсы не удаляются, пока на них есть зависимости.

## 10. HTTP, интерфейс и публикация

### 10.1. HTTP и UI

Новые страницы расположить в `resources/js/pages`: Series, Characters, Episodes.
Переиспользовать текущие layout, формы, таблицы и навигацию.
Начать с списка сцен и планов с явными кнопками порядка; сложный timeline editor
и отдельная drag-and-drop библиотека первой версии не требуются.

| Область маршрутов | Необходимые операции |
|---|---|
| Сериалы проекта | Список, создание, карточка, изменение паспорта, архивирование |
| Персонажи сериала | Карточка, draft-версия, загрузка/удаление неиспользуемого референса, утверждение |
| Эпизоды сериала | Создание, карточка, версия сценария, генерация/утверждение сценария |
| Планы версии | Старт дубля, просмотр результатов, остановка последующих шагов |
| Сборки эпизода | Сохранение manifest, сборка, просмотр, принятие |
| Публикации сборки | Запрос по выбранным каналам, состояние, reconciliation |

URI и named routes сохраняют текущую dot-нотацию (`projects.*`, далее `series.*`,
`episodes.*`). Общие сегменты задаются `Route::prefix()`, числовые параметры
ограничиваются, nested resources имеют scoped binding.
Один HTTP method + named route — один Controller с `__invoke` и один Feature-файл.

Ввод — Laravel Data DTO, преимущественно validation attributes. `rules()` только
для ограничений, которые нельзя выразить штатными атрибутами без custom Rule.
Использовать `#[CurrentUser]`, `#[Auth]`, `#[Config]` по назначению.
Resource выдаёт только подготовленные данные; eager loading находится в Tasks.

Сохранение формы и запуск генерации — разные действия. Предварительный просмотр
показывает сценарий, референсы, исходную точку и ограничения до запуска.
Кнопки затратных операций защищены server-side idempotency; disabled в UI лишь
помогает пользователю. Поле expected version защищает от потери изменений.

Inertia/Vue использует штатные формы и ограниченный polling только активных
операций. Сервер — источник истины после reload/reconnect; WebSocket для первой
версии не нужен. Не обновлять polling весь большой сценарий и все media.
Ошибка версии сохраняет введённый текст и предлагает обновить исходные данные.

### 10.2. Публикация

Новый request DTO публикации содержит стабильную ссылку на готовое медиа,
название, описание, номер эпизода и необходимые параметры канала.
Publisher получает transport-ready данные и возвращает нормализованный результат;
он не выбирает дубли и не изменяет канон. Legacy Prompt преобразуется в тот же
DTO, сохраняя существующий самостоятельный сценарий.

Перед отправкой сохранять PublicationRequest, проверять актуальность accepted
assembly, scope канала и уникальность запуска. Сохранить payload snapshot:
редактирование названия позже не должно незаметно менять повтор второго шага.
Для Instagram сохранять container ID и продолжать job по ID request, а не
сериализовать готовый экземпляр publisher с зависимостями.

Post создаётся после подтверждения внешней публикации и связывается с assembly.
Публикация по каналам имеет отдельные результаты; успех одного не выдаётся
за успех всех. Исторический Post не меняется при замене принятой сборки.

Сериальный Prompt не отправляет legacy-событие, запускающее автопубликацию;
дополнительно защитить listener от `shot_id != null`. Готовность дубля и
готовность эпизода — разные события. Уведомления о выпуске основаны на
подтверждённой публикации. TikTok/VK остаются существующими заглушками до
отдельной реализации интеграций.

## 11. Доступ, наблюдаемость и эксплуатация

### 11.1. Реальные границы доступа

Сейчас кабинет общий для допущенных пользователей; Project не принадлежит User.
План не предполагает уже существующего tenant scope или ролей владельца.
Сохранить принятую модель доступа и явно определить policies для генерации,
утверждения, публикации и чтения файлов. Авторизацию проверять на write boundary,
а для длительной job повторно согласно сохранённому actor и политике операции.

Независимо от пользовательских прав проверять parent scope:
проект → сериал → версия → сцена → план → дубль; канал относится проекту.
Нельзя прикрепить чужой character revision/media только по известному ID.
Секреты интеграций, prompts и приватные файлы не передавать в общие UI props,
логи либо сообщение Telegram. Новые business-события не требуют копирования
полного содержимого сценария в журнал.

### 11.2. Диагностика и восстановление

Логировать correlation IDs сериала, эпизода, версии, дубля, операции и remote task,
категорию ошибки, задержку и счётчик повторов. Не логировать токены и подписанные
URL с credentials. Доступность логов не заменяет понятный статус в кабинете.

Показывать очередь ожидания, возраст неизвестных операций, время до сохранения
медиа, ошибки скачивания, длительность FFmpeg, затраты/резервы и отказы принятия
из-за stale context. Пороговые значения выбирать по прототипу и наблюдаемой нагрузке.
Текст «ожидает результат» не выдаётся за подтверждённую работу worker.

Reconciler ограничен batch size, частотой, сроками и числом обращений к API.
Предусмотреть операторские действия «проверить remote ID», «повторить локальную
сборку», «создать новый дубль» и «разрешить неизвестный исход» с записью основания.
Оператор не должен вручную менять произвольные статусы в БД.

Backups должны включать БД и используемые оригиналы/готовые файлы. Перед полным
выпуском проверить восстановление связей manifest → media и приватного доступа
на изолированной среде. Наличие резервной копии без проверки восстановления
не подтверждает восстановимость проекта.

Не объединять доставку новой функции с массовым рефакторингом старого конвейера.

## 13. Тестовая матрица

| Граница | Сценарии регрессии | Наблюдаемые проверки |
|---|---|---|
| HTTP и scope | Без auth, неподтверждённый пользователь, неверный parent, недопустимое действие | Ответ, неизменность БД/файлов, отсутствие jobs и внешних эффектов |
| Версии | Правка draft, попытка правки approved, два клиента с одной версией | Старая версия сохранена, конфликт не теряет ввод, новый snapshot точен |
| Референсы | Правильные ракурсы, MIME/размер, неверный media ID, замена версии | Storage, checksum, отсутствие удаления используемого файла |
| Сценарий | Структура, участники, тайминги, переходы, превышение контекста | Точный persisted payload, field errors, нет платного следующего шага |
| Память | Draft/rejected последняя попытка, closed/open scene, чужой сериал | Выбран exact accepted source, правильные facts/anchors и pinned revisions |
| Генератор | Каждый поддержанный режим, неверная комбинация, смена глобальных настроек | Точный HTTP/CLI request и сохранённая конфигурация |
| Надёжность | Двойной submit, timeout, crash после отправки, repeated polling | Число внешних запусков, один receipt, unknown без нового платежа |
| Доставка | Commit без dispatch, результат без next dispatch, повтор job | Reconciler продолжает безопасный шаг, не повторяет неизвестный effect |
| Отмена | До старта и после remote ID, поздний success | Не стартуют новые стадии, результат не становится принятым |
| Монтаж | Порядок, trim, streams, отсутствующий/битый файл, повтор | Реально проверяемый файл/manifest, статус не ready при ошибке |
| Канон | Два accept, замена ранней серии, stale source | Одна canonical head, invalidation зависимостей, история сохранена |
| Публикация | Draft/shot/stale, double click, remote unknown, несколько каналов | Точный payload, один request/Post на результат, правильная версия media |
| Совместимость | Старый Prompt без shot, старые Post и standalone route/CLI | Старые контракты и история продолжают работать |

Правила тестов:

- Реальные HTTP routes через `route()`, factories/relations и реальные внутренние
  Actions/Tasks. В полном сценарии не подменять собственные слои.
- Отдельный Feature-файл на method + named route; Unit-файл — на один чистый класс.
  Проверки Laravel/БД/медиа — Feature. Короткие русские `test()`, без `$this`.
- Laravel/Pest helpers импортируются через `use function`; setup, действие
  и assertions разделяются пустыми строками. Цепочки методов — с переносами.
- Внешние границы закрывать framework fakes: точные HTTP routes с запретом
  неожиданных запросов, Process, Storage, Queue, Notifications и Laravel AI.
- Проверять payload, persistence и эффекты. Одного успешного HTTP status мало.
- Fixtures для локального FFmpeg небольшие и синтетические. Добавлять только
  нужные проверки выходного файла, не создавать платный media fixture в CI.
- Для конкуренции использовать отдельную тестовую БД/очередь Poster с контролем
  двух workers. Не использовать рабочую БД, B2B или чужие контейнеры.
- Имена тестов не дублируют реализацию; сохранять отдельные сценарии,
  обнаруживающие разные ошибки. Чисто оформительские изменения новых тестов не требуют.

Команды для соответствующего будущего этапа, не отчёт о выполнении:

```sh
docker compose exec -T --user appuser app php artisan test --compact tests/Feature/Actions/MakeShortActionTest.php
docker compose exec -T --user appuser app vendor/bin/pint --dirty --format agent
make stan
docker compose exec -T --user appuser app npm run typecheck
make npm-build
make pipe
```

Сначала запускать затронутые тесты, затем необходимые общие gates. Если сборка
или тест провалились, сначала определить причину; не подавлять PHPStan baseline
или blanket ignores. Обновление графа после изменений: `make graph-update`.
Для изменения только этих Markdown-планов PHP/DB/платные тесты не нужны.

## 14. Выпуск, откат и ограничения роста

1. Добавлять schema расширениями и nullable связями без переписывания всей истории.
2. Переключать только новый сериальный сценарий; standalone остаётся доступным.
3. Перед release проверить lifecycle старых queued jobs. При изменении сигнатуры
   сериализованных jobs обработать старые payload совместимо либо контролируемо
   завершить их до переключения; не очищать очередь для удобства.
4. Feature switch сериального сценария включать после готовности нужных workers
   и схемы. Отключение блокирует новые сериальные отправки, но сохраняет чтение
   результатов и безопасную обработку уже известных remote ID.
5. Откат кода не удаляет новые таблицы, receipts и файлы. После записи новых
   данных destructive down-миграции не являются планом operational rollback.
6. Внешнюю публикацию нельзя отменить rollback БД. Удаление/замена публикаций —
   самостоятельное явно порученное действие с собственными receipts.

Усложнение по измеримым причинам:

| Возможное расширение | Когда вводить |
|---|---|
| Сезоны | Появились правила нумерации/выпуска и структура сезона |
| Каталоги локаций/предметов | Их нужно независимо редактировать и переиспользовать |
| RAG / vector search | Bounded context/сводки не дают нужный поиск по большой истории |
| WebSocket | Ограниченный polling перестал удовлетворять UX/нагрузке |
| Отдельный render service | Подтверждена нехватка изоляции/масштабирования FFmpeg workers |
| Универсальный outbox | Несколько потребителей/интеграций требуют общей durable доставки |
| Сюжетные ветки | Нужны альтернативные каноны с явным выбором ветки |
| Multi-tenant модель | Появились независимые владельцы/команды и согласованная модель доступа |

## 15. Definition of Done полного первого выпуска

- [ ] Есть сценарии и референсы с версиями; старые результаты воспроизводимы
  по входам и происхождению, без обещания повторить случайный вывод модели.
- [ ] Оба вида продолжения доступны и основаны на принятой сборке/её финале.
- [ ] Работает сериал из нескольких эпизодов и нескольких планов в эпизоде.
- [ ] Реализованы речь и постоянный голос для заявленного диалогового формата.
- [ ] Отдельный дубль заменяется без перегенерации остальных независимых материалов.
- [ ] Канон обновляется только при принятии конкретного монтажа; invalidation работает.
- [ ] Двойные/поздние сообщения и неизвестные исходы не дают слепой повтор оплаты.
- [ ] Приватные референсы, scope, бюджеты и ограничение ресурсов проверены.
- [ ] Публикуется выбранная принятая версия, а не промежуточный Prompt.
- [ ] Старые shorts, исторические Post и незавершённые legacy jobs совместимы.
- [ ] Проверки пройдены в заявленной среде, пилот просмотрен, ограничения записаны.
- [ ] Локальные результаты, CI, deployment и production verification описаны раздельно.

## 17. Текущее состояние реализации

Ниже зафиксирован первоначальный локальный срез. После проверки deploy среда
разработки переведена на MySQL; актуальные изменения и проверки — в разделе 18.

Реализация находится в рабочем дереве без commit/push/deploy. Существующие shorts
и их Post сохранены. Новые миграции выполнялись в SQLite in-memory и отдельных
тестовых PostgreSQL; рабочая БД не мигрировалась. Генераторы и публикации в тестах
подменены на внешних границах, реальные платные вызовы не выполнялись.

| Этап | Реализовано и проверено локально | Оставшаяся граница |
|---|---|---|
| P0 | Structured Codex output, локальные attachments, DTO/capabilities видео, точные fake HTTP/CLI payload | Живая проверка аккаунтов, портретов, внешности и переходов |
| P1 | Модели, связи, nullable legacy FK, версии, factories, CRUD/архив и запрет удаления непустого проекта | Применение миграций к рабочей установке при выпуске |
| P2 | Приватные ракурсы, MIME/размеры, checksum, версии draft/approved, сохранение прежних файлов | Загрузка настоящих пользовательских наборов внешности |
| P3 | Ручной/генерируемый сценарий, schema/DTO, очередь, версии, утверждение, редактор сцен и планов | Качество сценария на выбранной модели и тематике |
| P4 | Exact accepted source, режимы continue/new shot/new scene, source time, bounded history, invalidation | Визуальная оценка фактического продолжения |
| P5 | Совместимый request DTO, обновлённые драйверы, pinned provider/model/duration/audio, private first frame | References/extend реализованы на границе драйвера; сериал использует first-frame pipeline |
| P6 | Durable операции, claim/poll/download/reconcile, cancellation intent, unknown, remote resolution, explicit abandon, лимит дублей | Наблюдение на реальном провайдере после допуска пилота |
| P7 | Frozen manifest, cut/trim, FFmpeg, private MP4/frame/tail, принятие и invalidation | Другие монтажные переходы и художественная приёмка |
| P8 | Native/silent, закреплённая voice specification, реплики в native prompt, mute результата и запрет silent dialogue | Постоянный голос не подтверждён; отдельные TTS/lip-sync, stems/mixing и субтитры не подключены |
| P9 | Series/Characters/Episodes, формы, редактор, источники, дубли, монтаж, recovery, доступ и ограниченное обновление результатов | Живой проход с настоящими материалами |
| P10 | Отдельная публикация принятого монтажа, PublicationRequest/Post, Instagram container, проверка receipts | Реальный OAuth/доступ каналов и явное поручение внешней публикации |
| P11 | Локальные quality gates, SQLite/PG сценарии, конкуренция, worker interruption, restore и browser preview | Платный пилот из трёх эпизодов и отдельный выпуск |

Фактические ограничения первого среза:

- Общий кабинет владельца и операторов. Независимые tenant-команды не введены.
- Сценарий: до 10 персонажей, 20 сцен, 100 планов, пяти минут; план 4–30 секунд,
  дополнительно проверяется диапазон конкретной модели. До 10 дублей на план.
- Context: до 64 КБ и 50 предыдущих принятых эпизодов; устаревшие и чужие события
  не включаются. Обязательный финал не обрезается ради лимита.
- Внешние ракурсы используются для генерации приватного первого кадра. При
  продолжении действия берётся выбранный кадр исходного видео, при смене ракурса
  он добавляется к референсам. Нативное продление хвоста видео не подключено
  к конвейеру сериалов до живого подтверждения transport и модели.
- Речь и музыка native создаются видеомоделью одним результатом. Voice blueprint
  служит инструкцией модели, а не гарантией идентичного тембра. ASR/TTS/lip-sync
  не добавлялись без выбранной и проверенной интеграции; тайминги субтитров
  из непроверенного сценария не выдумываются.
- Монтаж поддерживает последовательные склейки и обрезку, нормализует 720×1280,
  24 fps и аудио. Для silent входящий звук заменяется тишиной даже при ошибке
  провайдера. Независимые stems, музыка и эффекты отдельно не смешиваются.
- Публикация реализована для YouTube и Instagram. Unknown не превращается
  в повторную отправку. Явное abandoned сохраняет автора, причину и принятие
  неизвестного исхода; это не отмена remote-задачи и не доказательство отсутствия
  списания. Новый дубль требует отдельного действия.

### Подтверждённые проверки

- Полный Pest: **627 тестов / 3145 assertions**, SQLite in-memory, реальные
  внутренние Actions/Tasks и fakes внешних границ.
- Дополнительный PostgreSQL scope: **101 тест / 507 assertions** для сериалов,
  персонажей, эпизодов, дублей, сборки и контекста.
- Настоящий FFmpeg на синтетических локальных файлах: trim/MP4, финальный кадр,
  хвост, очистка временных файлов, ошибка сборки и фактически немой звук.
- Два независимых процесса PostgreSQL: один дубль на конкурентный request,
  один winner claim; два конкурирующих принятия дали одну canonical assembly
  и одно продвижение continuity, второе принятие отклонено как stale.
- Отдельный Redis namespace и worker: принудительная остановка после claim,
  восстановление unknown без повторного внешнего запуска; повтор download job
  не создал второй файл и не повторил HTTP. Внешний HTTP в опыте был fake.
- Dump/restore тестовой PostgreSQL и восьми приватных media в другую БД/каталог:
  проверены canonical pointers, ownership выбранных дублей, manifest checksums
  и равенство восстановленных файлов.
- PHPStan max без baseline/blanket ignores, Pint, Rector dry-run, ESLint,
  TypeScript, client/SSR build, Scribe и обновление локального Graphify.
- Browser preview на изолированной БД/файлах; мобильная ширина 390 px без
  горизонтального overflow. Проверки не доказывают CI или production.

### Что требует участия пользователя перед живым пилотом

1. Выполнить `make codex-login` в локальной установке. При последней проверке
   `make codex-status` вернул `Not logged in`; вход хоста не переносился.
2. Загрузить созданные в другом приложении ракурсы двух персонажей и выбрать
   профиль первого пилота. Утвердить версии внешности в кабинете.
3. Проверить ключ и доступ к выбранной видеомодели, согласовать бюджет живых
   проб. Выполнить три эпизода: открытая сцена → продолжение → новая сцена,
   заменить один дубль и оценить внешность, звук, стык и пригодность результата.
4. По результату проверить постоянство native-голоса; если оно недостаточно,
   выбрать отдельный speech/lip-sync путь, затем получать реальные тайминги
   для субтитров. Полный P8 и DoD диалогового выпуска пока не закрыты.
5. Для публикации проверить каналы/OAuth; YouTube receipt lookup требует read
   scope через `youtube:auth {channel_id} --with-read-verification`. Публикация,
   commit/push и deploy остаются отдельными явно порученными действиями.

Операционные команды и timeout chain находятся в
[deployment.md](deployment.md#очереди-сериалов-и-восстановление).

## 18. MySQL в локальной разработке и CI

После первого deploy обнаружено различие сред: production использует MySQL,
а первоначальные проверки выполнялись на SQLite и PostgreSQL. MySQL отклонил
строковые defaults у JSON-колонок в первом CREATE TABLE сериала. Эта миграция
не успела создать таблицы на production.

Исправлено и проверено локально:

- Docker Compose использует MySQL 8.4, отдельный `mysql_data`, адрес `db:3306`
  внутри сети и `127.0.0.1:3308` для хоста/IDE. PHP-образ содержит `pdo_mysql`
  и больше не устанавливает PostgreSQL driver.
- `.env.example`, `.env.docker.example` и существующие локальные DB-настройки
  переведены на MySQL. Остальные локальные ключи/настройки сохранены.
- `make test` / `make test-mysql` используют `phpunit.mysql.xml`, принудительно
  ограниченный базой `poster_test`. `make test-sqlite` сохраняет быстрый
  дополнительный прогон SQLite in-memory.
- CI поднимает настоящий MySQL service, применяет миграции и запускает полный
  Pest до упаковки и deploy. Отдельный SQLite-прогон остаётся обязательным.
- Из creation migration убраны 12 непереносимых JSON-defaults. Обязательные
  массивы сохраняются через существующие DTO/Tasks, включая начальный
  `EpisodeAssembly.continuity_snapshot=[]`.
- JSON в MySQL может менять порядок ключей объекта. Две проверки payload
  исправлены на сравнение значений; порядок элементов списков не игнорируется.
- Полный набор прошёл на MySQL и SQLite: **628 тестов / 3154 assertions**.
  Pint, Rector, PHPStan max, TypeScript и Scribe также прошли.
- Проверено обновление MySQL со старой схемы из 13 миграций до всех 17 на
  синтетических project/prompt/channel/post. Старые поля, данные и связи
  сохранились; standalone Prompt не получил `shot_id`.
- Новый Docker-образ собран и запущен; фактические driver/server проверены как
  MySQL 8.4, локальный `/up` возвращает HTTP 200.

До переключения сохранены dump локальной PostgreSQL, копии локальных env и
единственная настройка приложения. Пользовательских записей и контента в этой
локальной БД не было; настройка перенесена в MySQL с проверкой значения.
Старый `poster_postgres_data` не удалён. Синтетические PostgreSQL-проверки
раздела 17 остаются историческими результатами, а не текущей средой разработки.

Эти изменения сами по себе ещё не подтверждают успешный повторный deploy:
его результат необходимо проверить после commit/push и нового CI run.
